# jsjy-calendar

菁仕教育 AI 排课课表系统。

本项目用于逐步替代以飞书多维表格承载全部业务的旧课表方案，建立以中心数据库为唯一事实源、支持多人安全协作、AI 偏好管理、调课提案和个人课表查询的独立系统。

> 当前状态：产品与开发规划阶段，尚未初始化 Django 应用。请先阅读项目文档和领域定义，再开始实现。

## 为什么建设这个系统

现有飞书多维表格方案正在面临以下限制：

1. 每位老师和学生都需要独立课表视图，但视图数量接近平台上限；
2. 师生的模糊排课偏好依赖管理员记忆，调课提案需要反复修改课表和截图；
3. 多名管理员同时维护课表时，缺少可靠的冲突提示、版本控制、审计和通知；
4. 飞书同时承担数据存储、业务操作、权限隔离和展示，难以继续扩展；
5. 后续需要以低成本方式支持微信小程序个人课表。

## 产品目标

- PostgreSQL 作为正式课表唯一事实源；
- 管理员通过网页完成查询、排课、调课、取消和发布；
- 支持一对一课程与班课；
- 校验老师、学生、教室、校区营业时间和跨校区通勤冲突；
- 保存草稿、正式版本、操作审计和撤销记录；
- 使用 AI 解析并维护经管理员确认的师生偏好；
- 为单次调课生成多个无硬冲突、可解释的候选方案；
- 使用统一个人课表页面替代“每人一个飞书视图”；
- 将正式课表单向同步到飞书作为只读镜像；
- 为后续微信小程序和更完整的排课能力提供稳定基础。

## 核心原则

### 数据边界

- PostgreSQL 是唯一事实源；
- 飞书只接收单向同步，不反向覆盖数据库；
- GitHub 只保存代码、文档和脱敏测试夹具；
- 真实课表 CSV、生产数据、密钥和备份不得进入 Git。

### AI 边界

- AI 可以解析自然语言需求、生成草稿和解释候选；
- AI 不得直接发布或修改正式课表；
- 确定性规则引擎负责判断候选是否可行；
- 关键字段缺失时必须要求管理员确认，不能自行猜测；
- 首版不根据历史行为自动推断未明确表达的偏好。

### 协作边界

- 正式修改先进入草稿，经校验后由管理员发布；
- 并发修改使用乐观并发控制，不允许静默覆盖；
- 撤销通过创建反向新版本完成，不删除历史；
- 同一工作树同一时刻只允许一个实现型 Agent 修改代码；
- 产品、领域、权限、费用或架构决策必须交由主 Agent 和用户确认。

## MVP 范围

首个可用版本包括：

- 当前及未来课表的数据迁移与对账；
- 管理员飞书 OAuth 登录和白名单；
- 一对一与班课的手工排课；
- 周期授课计划与单次例外；
- 老师、学生、教室、校区和通勤冲突校验；
- 草稿、差异预览、发布、版本、审计和撤销；
- 师生个人课表安全链接；
- AI 偏好提取、人工确认和版本化更新；
- 单次调课的 3–5 个候选方案；
- 飞书多维表格单向同步；
- 管理员飞书机器人提醒；
- 国内云服务器部署、HTTPS、监控、备份和恢复演练。

MVP 明确不包括：

- 整学期全局自动排课；
- 移动其他课程的连锁重排；
- 根据历史行为自动学习偏好；
- 完整课费、收款、退款和财务对账；
- 师生微信自动通知；
- 微信小程序；
- 飞书反向写入；
- 全量历史数据迁移；
- 微服务、Kubernetes、Redis 或 Celery 集群。

## 计划技术栈

- Python；
- Django 单体应用；
- PostgreSQL；
- Django 服务端模板；
- 少量 HTMX 或原生 JavaScript；
- 数据库任务表和单一后台 Worker；
- Docker Compose；
- Caddy HTTPS 代理；
- 飞书开放平台 API；
- 支持结构化输出的云端大模型 API；
- 国内云服务器。

当前规模不需要微服务或复杂分布式基础设施。

## 数据说明

当前真实课表 CSV 仅保存在本地 `data/private/`，并已通过 `.gitignore` 排除。

现有数据已经暴露以下迁移风险：

- 旧“课程ID”是时间和姓名等信息拼接的展示值，不是可靠的不可变 ID；
- 班课学生使用逗号分隔字段保存，需要拆分为成员关系；
- “空出”同时表示可排和禁排等不同含义；
- 存在例会、团建等非教学排课项；
- 存在跨时区课程；
- 旧价格和取消比例只作为只读参考值保留；
- 旧冲突提醒中可能同时包含真实冲突、允许重叠和公式误报。

数据迁移必须产生数量、关联、异常和冲突对账报告。未经批准的 AI 分类结果不得影响正式排课。

## Subagents 协作方式

标准开发流水线：

```text
主 Agent 明确任务和验收
→ Scout 只读探索
→ 主 Agent 确认方案
→ 唯一 Worker 修改代码
→ Worker 运行测试并交接
→ Reviewer 并行只读评审
→ 主 Agent 筛选问题
→ 唯一 Fix Worker 修复
→ 复测和最终检查
→ Git 提交
```

禁止使用“根据 PRD 自行实现整个系统”之类的宽泛任务。每个 Worker 任务必须包含目标、范围、业务不变量、验收方式、交接内容和停止条件。

6. 生成可追溯的 commit 或 merge message；
7. 推送 `main`。

默认不强制推送、不绕过失败测试、不提交私有数据。涉及产品语义或无法判断意图的冲突必须先询问用户。

## 安全要求

- 不提交 `.env`、API 密钥、访问 token、数据库备份或真实课表数据；
- 生产数据库不暴露公网端口；
- 服务器使用 SSH 密钥登录；
- 正式环境必须启用 HTTPS；
- 每日备份到独立存储，并完成真实恢复演练；
- AI 不得接触数据库密码、飞书密钥或服务器凭证；
- Subagent 不得自行部署生产或执行破坏性迁移。
