# AI 排课课表系统 PRD

- **版本**：v0.1
- **状态**：试点规划
- **目标规模**：未来 12 个月内，学生不超过 500 人、老师不超过 100 人、管理员不超过 10 人
- **计划周期**：6–8 周进入首批真实试点
- **实施模式**：一名技术负责人借助 AI 开发，一名业务负责人持续提供规则与验收

## 1. 背景与问题

当前排课系统完全承载于飞书多维表格，正在触及以下能力上限：

1. 每位学生和老师需要独立课表视图，但多维表格最多支持约 200 个视图，无法继续扩展。
2. 老师和学生存在大量模糊、临时且会变化的排课偏好，目前依赖管理员记忆；调课提案依赖反复修改课表和截图，效率低、成本高。
3. 多名管理员共同维护课表时，缺少可靠的并发冲突提示、修改留痕、版本恢复和提交提醒。
4. 飞书多维表格同时承担数据存储、业务操作、权限隔离和展示，职责过多，难以继续演进。

## 2. 产品目标

建设一套独立的 AI 排课课表系统：

- 以中心数据库作为课表唯一事实源；
- 支持多人安全排课、冲突校验、版本留痕和通知；
- 使用 AI 解析并维护已确认的师生偏好；
- 针对单次调课需求生成多个可解释、无硬冲突的候选方案；
- 使用统一个人课表页面替代“每人一个飞书视图”；
- 将飞书降级为过渡期只读展示、管理员登录和通知渠道；
- 为后续微信小程序及更完整的课表产品打下数据和服务基础。

## 3. 核心产品原则

1. **中心数据库唯一事实源**：正式课表只允许从新系统写入。
2. **禁止双写**：飞书仅接受系统单向同步，不反向覆盖数据库。
3. **AI 只生成草稿**：AI 不得直接发布或修改已发布课表。
4. **规则与 AI 分工**：确定性规则负责可行性，AI 负责理解、排序和解释。
5. **草稿与正式版本分离**：所有变更先成为草稿，经校验后由管理员发布。
6. **不静默覆盖**：并发修改使用乐观并发控制，版本不一致时阻止提交。
7. **不删除历史**：撤销通过创建反向新版本完成，保留完整审计记录。
8. **先解决单次调课**：首版不尝试整学期自动排课或连锁重排。
9. **单体优先**：当前规模不建设微服务和复杂基础设施。

## 4. 用户与角色

### 4.1 管理员

- 通过飞书 OAuth 登录轻量网页；
- 仅飞书用户白名单中的人员可进入；
- MVP 中所有管理员同权，不建设复杂角色权限；
- 可查询课表、录入偏好、生成调课提案、创建草稿、发布、撤销及查看审计记录。

### 4.2 老师与学生

- 通过不可猜测、可撤销、可轮换的专属安全链接查看个人课表；
- 首版仅提供只读访问；
- 只能查看与本人或本人所属班级相关的课程。

### 4.3 AI

- 解析管理员粘贴的自然语言需求；
- 将模糊需求转换成待确认的结构化数据；
- 对确定性引擎生成的可行候选进行解释；
- 不直接发布课表，不自行猜测缺失的关键事实，不从历史课表自动推断偏好。

## 5. MVP 范围

### 5.1 数据迁移

- 迁移活跃学生、老师、班级、课程类型、校区、教室和已确认偏好；
- 迁移当前及未来课表；
- 旧历史数据保留为只读归档，不做全量历史清洗；
- 不假设旧表展示型“课程ID”是稳定唯一 ID；迁移前必须为人员、排课项及课程系列建立并验证不可变 ID；
- 旧表中含义混杂的“空出”不得直接导入为正式规则：AI 先生成批量分类草稿，业务负责人抽查并显式批准整个批次后才生效，分类批次必须可整体回滚；
- 导入后对账实体数量、课程数量、关联完整性和已有冲突。

### 5.2 课表管理

- 支持一对一课程与班课混合；
- 使用统一课程活动和参与者模型，不维护两套排课逻辑；
- 支持固定周期课、学期批量草案和临时约课的数据表达；
- 周期规则与每次真实课程实例分离；
- 支持请假、补课、单次调课、取消授课和恢复；取消授课保留原记录及变更历史；
- MVP 不计算单价、总价或取消费用；旧表价格和扣费比例仅作为只读参考值迁移、展示和同步，不参与排课规则；
- 课程时长来自少量标准时长集合；
- 开始时间按 15 或 30 分钟粒度搜索，具体粒度由现有业务数据确认。

### 5.3 冲突校验

发布前必须校验：

- 老师时间重叠；
- 学生时间重叠；
- 教室时间重叠；
- 校区营业时间；
- 老师跨校区最短通勤间隔；
- 课程时长和时间粒度合法性；
- 草稿基于的正式课表版本仍然有效。

通勤时间作为可配置业务数据，不写死在代码中。

### 5.4 AI 偏好管理

MVP 聚焦三类软偏好：

1. 日期和时间偏好；
2. 课程间隔偏好；
3. 校区和通勤偏好。

每条偏好至少包含：

- 适用对象；
- 偏好类型；
- 结构化规则；
- 低、中、高离散权重；
- 永久规则或临时例外；
- 有效开始和结束日期；
- 原始文本证据；
- 录入人和确认人；
- 当前状态及版本历史。

偏好录入流程：

1. 管理员粘贴聊天内容或录入口述摘要；
2. AI 提取结构化偏好；
3. 管理员逐项确认；
4. 确认后偏好才参与候选评分。

当新偏好与旧偏好冲突时，系统要求管理员选择：

- 永久替换；
- 指定日期范围内的临时例外；
- 追加条件。

旧记录不删除，保留版本和原始依据。首版不从历史排课自动推断未明确表达的偏好。

### 5.5 AI 单次调课提案

首版只处理单次调课，不移动其他课程，不产生连锁重排。

标准流程：

1. 管理员粘贴调课需求；
2. AI 识别老师、学生或班级、日期范围、课程时长、硬约束和软偏好；
3. 管理员确认结构化结果；
4. 确定性规则引擎从现有空档中枚举候选；
5. 过滤所有硬冲突；
6. 按已确认偏好计算分数；
7. 展示 3–5 个候选方案；
8. 每个方案展示满足的约束、牺牲的偏好、连带影响和评分明细；
9. 管理员选择方案并生成草稿；
10. 系统展示与当前正式课表的差异；
11. 发布前在事务中重新校验冲突和版本；
12. 管理员发布后生成不可变版本、同步飞书并创建通知待办。

如果缺少对象、日期、课时长度等关键字段，系统必须要求确认，AI 不得自行猜测。找不到候选时，系统应指出阻塞候选的具体硬约束。

### 5.6 多人协作与审计

- 每个可编辑对象带版本号；
- 管理员打开页面时记录当前版本；
- 提交时若版本已变化，阻止覆盖并展示他人的修改；
- 不使用长期独占锁；
- 每次发布记录操作者、时间、变更原因、变更前后差异和来源草稿；
- 撤销产生新的正式版本，不删除原版本。

### 5.7 飞书集成

飞书自建应用负责：

- 管理员 OAuth 登录；
- 飞书机器人提醒；
- 多维表格 API 单向同步。

同步要求：

- 通过飞书开放平台 API 实现，不以 MCP 或管理员电脑上的 Pi Agent 作为生产同步链路；
- 保存内部 ID 与飞书记录 ID 的映射；
- 每个同步任务有幂等键，重复执行不会创建重复课程；
- 同步失败可重试，并向管理员明确告警；
- 飞书同步失败不回滚已发布的数据库课表；
- 定期对账数据库与飞书镜像，发现漏同步或人工篡改；
- 飞书表格明确标识为只读镜像，切换后冻结人工编辑。

首版发布后仅通过飞书机器人提醒管理员，并生成可复制的师生通知文本。师生外部联系仍由管理员人工发送，系统记录待通知、已发送和已确认状态。

### 5.8 师生个人课表

- 使用一个统一的响应式个人课表页面；
- 不再为每位师生创建飞书视图；
- 安全链接中只包含随机 token，不包含姓名、学号等信息；
- 数据库只保存 token 哈希；
- token 可撤销和重新生成；
- 页面禁止搜索引擎收录；
- token 不进入普通应用日志；
- 记录必要的访问审计。

## 6. 用户故事

1. 作为管理员，我希望通过飞书身份登录系统，以免维护新的账号密码。
2. 作为管理员，我希望查询任意老师、学生、班级、教室或校区的课表，以便快速判断可用时间。
3. 作为管理员，我希望粘贴老师或学生的调课消息，由 AI 提取具体需求，以减少人工整理。
4. 作为管理员，我希望确认 AI 提取的对象、时间和偏好，以防错误信息进入正式规则。
5. 作为管理员，我希望为偏好设置作用范围和权重，以区分永久习惯与临时例外。
6. 作为管理员，我希望系统给出多个无冲突调课候选，以减少反复修改截图。
7. 作为管理员，我希望知道每个候选满足和牺牲了哪些偏好，以便向师生解释。
8. 作为管理员，我希望找不到候选时看到具体阻塞原因，而不是得到不可靠建议。
9. 作为管理员，我希望选择候选后先生成草稿，以便发布前确认差异。
10. 作为管理员，我希望发布前系统再次检查冲突和数据版本，以防基于过期课表提交。
11. 作为管理员，我希望他人已修改同一课程时系统阻止覆盖，以免丢失变更。
12. 作为管理员，我希望查看每次变更的操作者和前后差异，以便追责和恢复。
13. 作为管理员，我希望撤销错误修改但保留历史，以便审计。
14. 作为管理员，我希望飞书同步失败时收到提醒并能够重试，以免展示数据长期不一致。
15. 作为管理员，我希望发布后获得可复制的通知话术，以便快速通知老师和学生。
16. 作为老师，我希望通过专属链接查看自己的最新课表，而不需要寻找独立飞书视图。
17. 作为学生，我希望通过专属链接只看到与自己有关的课程，以便快速确认安排。
18. 作为运营负责人，我希望统计 AI 提案采用率和失败原因，以判断系统是否真正提高效率。
19. 作为业务负责人，我希望规则和偏好均可追溯到明确来源，以便纠正错误业务假设。
20. 作为系统维护者，我希望数据库可备份恢复、任务可重试且同步幂等，以降低生产事故风险。

## 7. 技术方案

### 7.1 技术栈

- Django 单体应用；
- PostgreSQL；
- Django 服务端模板配合少量 HTMX 或原生 JavaScript；
- 数据库任务表和单一后台 worker；
- 不在 MVP 引入 Redis、Celery、微服务或独立前端工程；
- 国内云服务器部署；
- 云端大模型 API，要求支持结构化输出；
- 飞书开放平台 API。

### 7.2 核心模块

1. **身份与访问模块**：飞书 OAuth、管理员白名单、个人课表安全链接。
2. **课表领域模块**：课程系列、课程实例、参与者、资源占用和状态变更。
3. **约束引擎**：时间、教室、校区、营业时间和通勤校验。
4. **偏好模块**：结构化偏好、权重、有效期、版本和原文证据。
5. **提案模块**：需求解析、空档枚举、候选过滤、评分与解释。
6. **发布与审计模块**：草稿、正式版本、乐观并发、差异和撤销。
7. **集成模块**：飞书同步、机器人通知、幂等任务和定期对账。

### 7.3 核心数据实体

- 人员、老师、学生；
- 班级和成员关系；
- 课程类型和标准时长；
- 校区、教室和校区间通勤时间；
- 周期课程系列；
- 单次课程实例；
- 统一资源占用；
- 偏好、偏好版本和偏好来源；
- 调课请求、候选方案和评分明细；
- 草稿变更和正式版本；
- 审计事件；
- 后台任务和飞书记录映射；
- 个人访问 token 哈希。

老师、学生和教室统一建模为资源占用。数据库负责阻止同一资源时间区间重叠，应用层负责通勤、营业时间及其他跨记录规则。

### 7.4 AI 与确定性逻辑边界

AI 可以：

- 将自然语言转换成结构化草稿；
- 生成需要管理员确认的问题；
- 根据已计算的评分结果生成解释；
- 总结本次方案的影响。

AI 不可以：

- 直接读写正式课表；
- 自行判断时间段是否冲突；
- 绕过规则引擎提供不可行候选；
- 从历史行为自动生成正式偏好；
- 在关键数据缺失时自行补全事实。

## 8. 数据与隐私边界

原型阶段允许直接调用云端 AI 处理真实文本，不建设复杂脱敏管线。但在正式扩大使用前必须完成以下上线门槛：

- 明确隐私告知和授权；
- 确认模型供应商的数据使用和不训练条款；
- AI 永远不能接触数据库密码、飞书应用密钥或服务器凭证；
- 最小化发送给模型的字段；
- 记录模型调用和操作审计；
- 对可能涉及未成年人的个人信息完成合规评估。

## 9. 成功指标

### 9.1 主指标

- AI 单次调课候选的提案采用率。

试点开始时不预设固定目标比例。先通过 1–2 周影子测试建立人工基线，再根据真实样本设定提升目标。

### 9.2 强制质量护栏

- 被系统标记为可行的候选，硬冲突漏检率必须为 0；
- 正式发布不得发生静默并发覆盖；
- 飞书同步重试不得创建重复课程；
- 每次正式发布均可追溯和撤销。

### 9.3 辅助指标

- AI 结构化结果的人工修正率；
- 从粘贴需求到生成可发布草稿的耗时；
- 无候选需求的原因分布；
- 飞书同步成功率和平均延迟；
- 管理员持续使用率。

## 10. 测试与验收

测试只验证外部行为和业务不变量，不针对实现细节堆积用例。

必须覆盖：

1. 一对一和班课的创建、调课、取消及周期例外；
2. 老师、学生和教室重叠冲突；
3. 跨校区通勤间隔；
4. 偏好永久替换和临时例外；
5. AI 输出缺字段、结构错误、超时和拒绝服务；
6. 候选排序和评分明细；
7. 两名管理员并发修改同一课程；
8. 发布事务中课表已变化；
9. 飞书超时、限流、重复执行和对账；
10. 安全链接生成、访问、撤销和轮换；
11. 数据迁移数量、外键和冲突对账；
12. 数据库备份恢复演练。

## 11. 实施计划

### 第 1 周：领域与数据盘点

- 接收每表 CSV、字段字典和关联说明；
- 梳理领域词汇、硬约束、软偏好和例外；
- 收集 30–50 条真实调课需求及最终处理结果；
- 形成字段映射、迁移风险和规则清单。

### 第 2 周：数据底座

- 建立 Django、PostgreSQL 和核心数据模型；
- 实现统一资源占用和冲突校验；
- 试导入当前及未来课表并完成对账。

### 第 3 周：正式排课工作流

- 飞书 OAuth 和管理员白名单；
- 课表查询、创建、调课和取消；
- 草稿、发布、审计、撤销和乐观并发控制。

### 第 4 周：偏好与候选引擎

- AI 结构化提取和人工确认；
- 偏好版本、权重及有效期；
- 空档枚举、硬约束过滤和软偏好评分。

### 第 5 周：提案界面与个人课表

- 候选比较、评分解释和差异预览；
- 师生响应式个人课表；
- 安全链接生成、撤销和访问控制。

### 第 6 周：飞书集成与运维

- 多维表格单向同步；
- 机器人提醒；
- 幂等任务、重试、对账、备份和基础监控。

### 第 7 周：影子试点

- 1–2 名管理员和部分典型师生参与；
- 新系统给方案，旧流程继续正式执行；
- 建立采用率和修正率基线，修正数据与规则。

### 第 8 周：真实试点

- 试点范围冻结飞书人工编辑；
- 新系统正式发布，飞书只读镜像；
- 每日复盘失败案例；
- 决定扩大范围、继续整改或暂停。

## 12. 上线与回退

- 切换前完成一次完整导入和对账；
- 试点范围内冻结飞书写权限；
- 数据库成为唯一写入口；
- 飞书同步失败不影响数据库正式状态；
- 严重故障时停止新发布，保留只读课表和旧飞书归档；
- 回退不得重新开启长期双写；
- 每日自动备份到独立位置，并完成至少一次恢复演练。

## 13. 风险与应对

| 风险 | 应对方式 |
|---|---|
| 隐性排课规则未被记录 | 由业务负责人持续提供真实案例并逐条确认规则 |
| AI 错误理解需求 | 结构化结果必须经管理员确认，缺失字段必须追问 |
| AI 生成冲突方案 | AI 不负责可行性，候选必须通过确定性规则引擎 |
| 多人修改互相覆盖 | 版本号和乐观并发控制 |
| 飞书同步失败或重复 | Outbox 任务、幂等键、重试和定期对账 |
| 安全链接泄露 | 随机 token、哈希存储、可撤销和访问日志 |
| 迁移数据不一致 | 数量、外键、冲突三类对账，旧表只读归档 |
| MVP 范围失控 | 坚持单次调课、无连锁重排、单体应用和单一管理员角色 |
| 管理员不愿改变流程 | 先影子试点，使用真实采用率和耗时评估价值 |

## 14. 明确不在本 PRD 范围内

- 整学期全局自动排课；
- 多步或一步连带调课；
- 自动移动其他课程；
- 根据历史行为持续学习偏好；
- 老师风格、性别或资历匹配；
- 师生自动微信通知；
- 微信小程序；
- 飞书反向写入数据库；
- 全量历史数据迁移；
- 按校区隔离和细粒度 RBAC；
- 微服务、Redis、Celery、事件总线等扩展架构。

## 15. 后续演进

1. 师生本人填写标准偏好表单；
2. 支持一步连带调课；
3. 老师飞书自动通知和确认回执；
4. 微信小程序登录及个人课表；
5. 请假、调课申请和确认流程；
6. 多校区权限隔离；
7. 在真实需求证明必要后，引入 OR-Tools 等约束求解器完成整学期排课。

## 16. 启动所需材料

首轮数据盘点使用每表 CSV，需同时提供：

- 每张表的 CSV 导出；
- 字段名称、字段类型、业务含义、唯一性和关联表；
- 表间关联关系；
- 公式字段、自动化规则和关键视图筛选条件；
- 已知数据异常；
- 现有唯一 ID 说明；
- 30–50 条真实调课需求及最终处理结果；
- 当前硬约束、软偏好和人工例外规则。

首个正式产出应是字段映射、领域模型修订、迁移风险报告和缺失规则清单，而不是直接开始开发页面。
