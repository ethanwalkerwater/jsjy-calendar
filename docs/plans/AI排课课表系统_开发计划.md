# AI 排课课表系统开发计划

- **依据**：[AI排课课表系统 PRD](../product/AI排课课表系统_PRD.md)
- **状态**：待执行
- **适用方式**：个人主导、Vibe Coding、Pi Agent + Subagents 辅助
- **目标规模**：学生 500 人以内、老师 100 人以内、管理员 10 人以内

## 1. 计划结论

本项目应采用“串行里程碑 + 阶段验收”的方式开发，不能让多个 Subagent 同时在同一代码目录内自由实现不同功能。

对于首次独立开发和部署服务器的开发者，原 PRD 中 6–8 周进入真实试点偏激进。建议按实际投入调整：

- 每周投入 30 小时以上：约 8–10 周进入真实试点；
- 每周投入 15–20 小时：约 12–16 周；
- 每周投入不足 10 小时：不承诺日期，只按阶段验收推进。

开发顺序必须是：

```text
项目与数据基础
→ 确定性排课核心
→ 管理员工作流
→ 个人课表
→ AI 偏好与提案
→ 飞书同步
→ 部署与影子试点
→ 真实试点
```

AI 功能不能先于排课核心，因为 AI 候选必须依赖可信的时间、参与者、资源和冲突数据。

## 2. 开发原则

### 2.1 单一事实源

- PostgreSQL 是正式课表唯一事实源；
- 飞书是只读镜像，不允许反向覆盖数据库；
- GitHub 只保存代码、文档和不含隐私的测试夹具；
- 生产数据、CSV 原始文件、密钥和数据库备份不得提交到 GitHub。

### 2.2 单写者原则

- 同一工作目录同一时刻只能有一个实现型 Agent 修改代码；
- 可以并行运行多个只读 Scout、Reviewer 或 Researcher；
- 不允许多个 Worker 在同一工作树中并行修改不同文件，除非已经建立独立 Git Worktree、明确文件所有权和合并顺序；
- 项目早期默认不使用并行 Worker，优先串行完成小里程碑。

### 2.3 小任务原则

每个开发任务应控制在 0.5–2 天，最长不超过 3 天。任务必须明确：

- 要解决的一个具体问题；
- 可以修改的模块；
- 禁止扩展的范围；
- 可观察的验收结果；
- 必须运行的测试或人工流程；
- 遇到产品、架构、费用或权限决策时停止并上报。

### 2.4 阶段门原则

- 当前阶段未通过验收，不进入下一阶段；
- 不以“页面能打开”作为完成标准；
- 每阶段必须同时留下代码、测试、操作文档和验证证据；
- 所有生产发布先经过 Staging 环境验证。

## 3. 推荐项目结构

当前目录已初始化为 Git 仓库，开发文档和私有数据按以下结构管理：

```text
/
├── .gitignore
├── Makefile
├── .env.example
├── compose.yml
├── docs/
│   ├── README.md
│   ├── product/
│   │   └── AI排课课表系统_PRD.md
│   ├── domain/
│   │   └── CONTEXT.md
│   ├── plans/
│   │   └── AI排课课表系统_开发计划.md
│   ├── adr/
│   ├── development/
│   ├── runbooks/
│   └── handoffs/
├── data/private/        # 本地真实数据，Git 忽略
├── config/
├── scheduler/
├── templates/
├── static/
├── tests/
└── manage.py
```

约定：

- `docs/domain/CONTEXT.md`：只保存排课领域术语，不保存技术实现；
- `docs/development/AGENTS.md`：告诉所有 Agent 项目边界、命令、禁止事项和验收流程；
- `docs/adr/`：只记录难以逆转且存在真实权衡的决定；
- `docs/plans/`：阶段实施计划；
- `docs/runbooks/`：部署、备份、恢复、飞书授权等小白操作手册；
- `docs/handoffs/`：Subagent 阶段交接记录；
- 原始 CSV 保存在被 `.gitignore` 排除的 `data/private/`。

建议首批 ADR：

1. PostgreSQL 为唯一事实源，飞书仅作单向镜像；
2. AI 只生成草稿，确定性引擎决定候选是否可行；
3. 使用 Django + PostgreSQL 单体，不建设微服务。

## 4. 本地与生产技术基线

### 4.1 本地开发

- Python 当前稳定版本；
- Django；
- PostgreSQL；
- Django 模板 + 少量 HTMX 或原生 JavaScript；
- Docker Desktop 或同类容器环境，仅用于统一 PostgreSQL 和后续部署环境；
- Git + 私有 GitHub 仓库；
- 单元测试使用 Django 自带测试能力或 pytest，二选一，不并存两套风格；
- 一个后台 Worker 从数据库任务表读取 AI、飞书同步和通知任务。

### 4.2 生产部署

初期只使用一台国内云服务器：

- Ubuntu LTS；
- 建议最低 2 核 CPU、4 GB 内存、80 GB 云盘；
- Docker Compose 运行 Web、Worker、PostgreSQL 和 Caddy；
- Caddy 自动配置 HTTPS；
- 仅开放 80、443 和受限 SSH 端口；
- SSH 只允许密钥登录；
- 域名解析到服务器；
- 数据库不暴露公网端口；
- 每日加密备份到独立对象存储；
- 飞书机器人接收应用异常、任务失败和备份失败提醒。

当前规模不使用 Kubernetes、微服务、Redis、Celery、消息队列集群或多服务器部署。

### 4.3 最小命令入口

使用简单 Makefile 固定常用命令，避免你和 Subagent 各自发明不同操作方式：

```text
make setup      初始化本地环境
make dev        启动开发环境
make test       运行测试
make check      运行迁移检查和静态检查
make backup     创建数据库备份
make restore    在测试环境恢复备份
make deploy     部署到 Staging 或生产
```

具体命令在项目初始化阶段确定；不要为了命令封装引入额外工具。

## 5. 开发阶段

## 阶段 0：项目启动与安全护栏

**预计时间**：2–4 天

### 目标

建立一个任何 Agent 都能理解、运行、测试和安全修改的项目骨架。

### 工作项

1. 为当前 Git 仓库创建私有 GitHub 远程仓库；
2. 初始化 Django、PostgreSQL 和 Docker Compose；
3. 创建 `.env.example` 和 Makefile，继续维护现有 `.gitignore` 与 `docs/README.md`；
4. 继续维护 `docs/domain/CONTEXT.md`；
5. 创建 `docs/development/AGENTS.md`，写明：
   - PostgreSQL 是唯一事实源；
   - AI 不得直接发布课表；
   - 一个工作树只允许一个 Writer；
   - 生产数据和密钥不得写入仓库；
   - 发现产品决策时必须停止并交还主 Agent；
6. 建立最小 CI：每次提交自动运行测试和迁移检查；
7. 创建开发、测试、Staging、生产四套环境变量说明；
8. 创建第一份空白部署和恢复 Runbook。

### 阶段验收

- 新电脑按 `docs/README.md` 和开发指南能在 30 分钟内启动项目；
- `make test` 成功；
- 数据库迁移可以从零执行；
- GitHub 中不包含真实 CSV、密钥或 `.env`；
- Subagent 只阅读 `docs/README.md`、`docs/domain/CONTEXT.md`、`docs/development/AGENTS.md` 即可说清项目边界。

## 阶段 1：数据盘点与领域模型

**预计时间**：1–2 周

### 目标

先证明系统正确理解现有数据，再开始写正式业务功能。

### 已知数据问题

- 现有“学员课程ID”和“老师课程ID”是由时间、姓名等拼接的展示值，并非可靠不可变 ID；
- 班课学生被放在逗号分隔字段中；
- 部分学生缺少数字编号；
- “空出”同时表达可排与禁排等不同含义；
- 存在例会、团建等非授课排课项；
- 存在时差课程；
- 价格与取消比例只作为只读参考值，不由新系统计算；
- 旧表冲突提醒包含大量记录，含义待分类。

### 工作项

1. 编写只读 CSV 数据分析命令；
2. 输出字段字典、空值率、重复率、时间范围和异常值报告；
3. 为新系统建立不可变内部 ID；
4. 建立旧记录到新实体的映射表；
5. 确认并实现以下领域对象：
   - 人员；
   - 班级及成员；
   - 课程产品；
   - 周期授课计划；
   - 单次授课安排；
   - 非教学排课项；
   - 可排时段；
   - 禁排时段；
   - 校区、教室和在线地点；
   - 时区；
6. “空出”采用 AI 批量分类草稿，业务负责人抽查并整批批准后生效；
7. 明确旧冲突提醒哪些是脏数据、公式误报或允许场景；
8. 编写可重复执行的导入脚本；
9. 导入使用事务，失败时不留下半成品；
10. 每次导入生成数量、关联、异常和冲突对账报告。

### 阶段验收

- 相同 CSV 重复导入不会创建重复人员或授课安排；
- 每个班课学生都变成独立成员关系，不再依赖逗号字符串；
- 每条旧记录都有“成功映射、明确跳过或待人工处理”状态；
- 所有歧义“空出”在批准前不影响候选；
- 业务负责人抽查至少 50 条映射结果并确认；
- `docs/domain/CONTEXT.md` 中不存在仍被混用的核心术语。

### 阻塞下一阶段的决策

- “课程产品、周期计划、单次授课”正式名称和边界；
- 时差字段代表老师时区、学生时区还是课程显示时区；
- 例会、团建、请假等事项是否全部作为硬占用；
- 新授课安排的价格参考值由飞书公式、人工还是其他系统提供；
- 冲突提醒中哪些重叠是业务允许的。

## 阶段 2：确定性排课核心

**预计时间**：1–2 周

### 目标

建立不依赖 AI 和页面的可信排课引擎。

### 工作项

1. 建立授课安排、参与者、地点和资源占用；
2. 支持一对一和班课；
3. 支持标准时长及统一时间粒度；
4. 支持周期计划生成单次授课安排；
5. 支持单次例外，不污染整个周期；
6. 实现硬约束：
   - 老师重叠；
   - 学生重叠；
   - 教室重叠；
   - 校区营业时间；
   - 跨校区通勤间隔；
   - 时区转换；
7. 支持取消授课但保留原记录；
8. 实现候选空档枚举，暂不做偏好排序；
9. 数据库层负责可表达的重叠约束，应用层负责通勤等跨记录规则；
10. 所有发布操作在数据库事务中再次校验。

### 阶段验收

- 一对一、班课、线上课、跨校区课均有可运行测试；
- 同一老师、学生或教室不能被重复占用；
- 取消后的授课安排保留审计信息，但不继续占用资源；
- 周期课单次调课不改变其他日期；
- 候选引擎不会返回任何硬冲突时间；
- 使用历史样例回放时，冲突结果可由业务负责人解释。

---

## 阶段 3：管理员排课工作流

**预计时间**：1–2 周

### 目标

先让管理员不依赖 AI 也能安全完成正式排课。

### 工作项

1. 飞书 OAuth 登录；
2. 管理员白名单；
3. 课表按老师、学生、班级、教室和校区查询；
4. 创建、调课、取消和恢复；
5. 草稿、差异预览和发布；
6. 乐观并发控制；
7. 操作者、时间、原因和前后差异审计；
8. 撤销通过反向新版本完成；
9. AI 和飞书不可用时仍可手工排课。

### 阶段验收

- 两名管理员同时修改同一授课安排时，后提交者被阻止并看到差异；
- 任何正式修改都能追溯；
- 发布前硬约束再次校验；
- 手工完成一次调课不超过当前流程的主要操作步骤；
- 业务负责人可以只使用页面完成一整套演练。

## 阶段 4：师生个人课表

**预计时间**：3–5 天

### 目标

替代“每人一个飞书视图”，先解决 200 个视图上限。

### 工作项

1. 响应式个人课表页面；
2. 老师、学生和班级关联课表查询；
3. 不可猜测的随机访问 token；
4. 数据库只保存 token 哈希；
5. token 撤销和重新生成；
6. 页面禁止搜索引擎收录；
7. token 不进入普通日志；
8. 记录必要访问审计。

### 阶段验收

- 新增第 201 名学生不需要创建飞书视图；
- 学生链接不能查看其他学生数据；
- 链接撤销后立即失效；
- 手机浏览器可清晰查看未来课程；
- 链接泄露处理流程有 Runbook。

---

## 阶段 5：AI 偏好与单次调课提案

**预计时间**：1–2 周

### 目标

在可信排课核心之上加入 AI，而不是让 AI 替代规则引擎。

### 工作项

1. 定义 AI 结构化输出 Schema；
2. 管理员粘贴调课文本；
3. AI 提取对象、日期范围、时长、硬约束和软偏好；
4. 管理员逐项确认后才保存；
5. 支持时间、课程间隔、校区通勤三类偏好；
6. 支持低、中、高权重；
7. 支持永久偏好和临时例外；
8. 新旧偏好冲突时选择替换、例外或追加；
9. 确定性引擎枚举和过滤候选；
10. 规则代码计算评分明细；
11. AI 只负责把评分结果解释成自然语言；
12. 展示 3–5 个候选及无候选原因；
13. 选择候选后只生成草稿；
14. 保存模型、提示词版本、结构化结果和人工修正结果；
15. 模型超时、限流或结构错误时可重试或回到手工流程。

### 阶段验收

- AI 不能直接写正式授课安排；
- AI 给出的时间必须来自确定性候选集合；
- 缺少关键字段时系统要求确认，不自行猜测；
- 每个候选可解释满足和牺牲了哪些偏好；
- 使用至少 30 条历史调课需求进行离线回放；
- 记录 AI 提取修正率和候选采用情况；
- 删除 AI 功能后，手工排课核心仍然完整可用。

---

## 阶段 6：飞书单向同步与通知

**预计时间**：1 周

### 目标

让飞书稳定展示数据库中的正式结果，但不重新成为事实源。

### 工作项

1. 飞书自建应用和权限清单；
2. 内部 ID 与飞书记录 ID 映射；
3. Outbox 数据库任务表；
4. 单一 Worker 处理同步；
5. 幂等键、指数退避、失败重试和死信状态；
6. 定期对账数据库与飞书；
7. 发布后飞书机器人提醒管理员；
8. 生成可复制的师生通知文本；
9. 飞书字段变更检测；
10. 冻结试点范围内的飞书人工写入。

### 阶段验收

- 同一任务执行多次不会产生重复记录；
- 飞书断网或限流后可自动恢复；
- 数据库发布成功但飞书失败时，页面明确显示同步状态；
- 对账可以发现被人工修改或漏同步的记录；
- 飞书故障不阻塞管理员继续查看数据库课表。

---

## 阶段 7：部署、备份和 Staging 演练

**预计时间**：1 周

### 目标

在真实试点前证明你能够部署、监控、备份和恢复，而不只是让代码在本机运行。

### 工作项

1. 购买国内云服务器和域名；
2. 完成备案或提前确认所需流程；
3. 配置 SSH 密钥、防火墙和自动安全更新；
4. 使用 Docker Compose 部署 Staging；
5. 配置 HTTPS；
6. 配置数据库每日备份到独立对象存储；
7. 在空数据库中执行完整恢复；
8. 配置健康检查、磁盘空间和任务失败提醒；
9. 编写以下 Runbook：
   - 首次部署；
   - 日常发布；
   - 数据库备份；
   - 数据库恢复；
   - 回滚代码版本；
   - 飞书授权失效；
   - 安全链接泄露；
   - AI 服务不可用；
10. 不允许 Subagent 直接持有生产服务器和生产数据库的长期权限。

### 阶段验收

- 从一台新电脑按文档可完成 Staging 发布；
- 在测试环境成功恢复一次备份；
- 关闭 AI 或飞书服务后核心手工排课仍可用；
- 非开发人员能看懂故障时应该联系谁、停止什么操作；
- 生产密钥不出现在 Git、聊天记录和 Agent 输出中。

---

## 阶段 8：影子试点与真实试点

**预计时间**：2–3 周

### 影子试点

1. 选择 1–2 名管理员和一批典型师生；
2. 新系统读取真实数据并生成提案；
3. 旧流程继续作为正式执行路径；
4. 比较候选、耗时、人工修正和失败原因；
5. 每日复盘异常，不用修改提示词掩盖领域或数据问题；
6. 修复后重复历史回放和人工流程。

### 真实试点

1. 再次全量导入并对账；
2. 冻结试点范围飞书写权限；
3. 新系统成为唯一写入口；
4. 飞书仅作镜像；
5. 每日检查同步、任务、访问和错误日志；
6. 任何不可解释的硬冲突立即暂停新发布；
7. 严重故障时停止发布，但保留个人课表只读访问。

### 阶段验收

- 被标记为可行的候选硬冲突漏检为 0；
- 没有静默并发覆盖；
- 所有发布可追溯和撤销；
- 飞书重试不产生重复记录；
- 建立首版提案采用率基线；
- 管理员愿意继续使用，而不是绕回飞书直接编辑；
- 完成继续扩大、继续整改或停止试点的书面决定。

## 6. Subagents 开发方法

## 6.1 角色分工

### 主 Agent（你当前对话中的总控）

- 阅读 PRD、CONTEXT、ADR 和当前代码；
- 拆分阶段和任务；
- 判断哪些是用户决策；
- 决定是否接受 Reviewer 建议；
- 控制唯一 Writer；
- 最终检查差异、测试和文档；
- 不把产品或架构决策交给 Subagent 自行决定。

### Scout

- 只读探索代码、数据和文档；
- 输出实现入口、现有模式、风险和待决问题；
- 不修改代码。

### Worker

- 每次只实现一个已批准的小任务；
- 是当前工作树唯一写者；
- 发现范围外决策必须停止并上报；
- 返回修改文件、测试结果、未完成内容和风险。

### Reviewer

使用全新上下文直接阅读代码和差异，分别检查：

- 正确性和回归；
- 测试与验收覆盖；
- 简单性和可维护性；
- 涉及登录、token、密钥、个人数据时增加安全角度；
- 涉及飞书、AI、部署时增加集成和故障恢复角度。

### Researcher

只在需要当前官方资料时使用，例如：

- 飞书开放平台 OAuth 和多维表格 API；
- 微信小程序备案与登录；
- 云服务器安全配置；
- 当前模型结构化输出能力。

必须优先查官方文档，并返回来源链接和版本日期。

## 6.2 每个任务的标准流水线

```text
主 Agent 明确任务和验收
→ Scout 只读侦察（必要时）
→ 主 Agent 确认实现方案
→ 唯一 Worker 修改代码
→ Worker 运行测试并交接
→ 多个 Reviewer 并行只读评审
→ 主 Agent筛选应修问题
→ 唯一 Fix Worker 修复
→ 复测和必要的二次评审
→ 主 Agent检查最终 diff
→ 提交 Git
```

不能在 Worker 实现完成后直接宣布任务结束。Worker 的报告只是证据，必须经过独立 Review 和主 Agent 验收。

## 6.3 子代理任务模板

每次交给 Worker 的提示应包含：

```text
目标：只实现哪一个可观察结果。
依据：PRD、CONTEXT、ADR 和阶段计划的具体章节。
允许修改：模块或文件范围。
禁止事项：不得扩展的功能、不得修改的契约。
业务不变量：必须始终成立的规则。
验收：要运行的命令和人工流程。
交接：修改文件、实现内容、未完成项、命令及退出码、风险、需用户决定的问题。
停止条件：遇到产品、架构、权限、费用、部署或范围决策时停止并上报。
```

不要使用“把整个系统实现完”“根据 PRD 自行完成”等宽泛提示。

## 6.4 Lane Board

只有确实需要多个独立 Worktree 时，主 Agent 先记录：

| Lane | 工作目录 | 负责决策/功能 | 文件或契约边界 | 隔离路径 | 权限 | 下一验收门 | 交接文件 |
|---|---|---|---|---|---|---|---|
| core | 主 worktree | 排课核心 | 领域模型与约束接口 | 主目录 | 唯一写者 | 核心测试 | docs/handoffs/core.md |
| docs-review | 主目录 | 文档一致性检查 | 只读 | 无 | 只读 | 文档评审 | docs/handoffs/docs-review.md |

项目早期不建议创建多个实现 Lane。优先让一个 Worker 串行完成核心功能，Reviewer 并行读取。

## 6.5 Subagent 常见失败及预防

### 失败 1：不同 Agent 发明不同领域词汇

预防：每次任务先读 `docs/domain/CONTEXT.md`；发现新歧义时先回到主 Agent，不在代码里自行命名。

### 失败 2：Worker 顺手扩展范围

预防：提示中写明非目标；每个任务最多一个主要结果；发现产品决策立即停止。

### 失败 3：多个 Writer 修改同一模块

预防：默认一个 Writer；必须并行时使用独立 Worktree 和 Lane Board。

### 失败 4：测试只验证 Agent 自己的实现

预防：先写验收契约，再实现；Reviewer 从 PRD 和业务不变量出发检查，不沿用 Worker 推理。

### 失败 5：只看测试通过，不使用真实流程

预防：每阶段至少有一个手工用户流程；UI 使用浏览器实际操作；同步测试真实错误与重试；备份必须真实恢复。

### 失败 6：Agent 接触生产密钥或真实隐私数据

预防：使用假数据和测试应用；生产 `.env` 只在服务器配置；不把密钥粘贴进对话。

### 失败 7：长任务中断后不清楚改了什么

预防：任务小于 3 天；Worker 每次返回 handoff；提交前检查 `git diff` 和测试状态。

### 失败 8：Reviewer 提出大量可选重构导致失控

预防：主 Agent 将建议分为“阻塞、现在修、以后再做、忽略”；只把前两类交给 Fix Worker。

### 失败 9：Subagent 使用过期外部 API 信息

预防：涉及飞书、微信、云平台和模型 API 时，由 Researcher 查询官方文档并记录日期。

### 失败 10：Agent 在脏工作树继续开发

预防：每个任务开始前检查 `git status`；上一任务未提交或未交接时不开新 Writer。

## 7. 测试策略

### 7.1 测试金字塔

1. 领域规则单元测试：冲突、周期例外、时区、偏好评分；
2. 数据库集成测试：事务、并发、资源重叠、导入幂等；
3. 页面流程测试：管理员创建、调课、发布和撤销；
4. 外部集成契约测试：AI 结构化输出、飞书同步、重试和对账；
5. 少量端到端流程：从调课需求到个人课表展示。

### 7.2 固定业务夹具

从真实数据中制作脱敏小样本，至少包含：

- 普通一对一；
- 多学生班课；
- 老师例会占用；
- 老师跨校区；
- 网课；
- 时差课程；
- 临时取消；
- 周期课单次例外；
- 同名或缺少旧编号的人员；
- 并发修改；
- 无可行候选。

夹具不包含真实姓名、手机号、访问 token 或费用隐私。

### 7.3 关键不变量

- 正式数据只能通过发布流程产生；
- AI 永远不能直接发布；
- 同一资源不得存在不允许的时间重叠；
- 取消授课不删除历史；
- 飞书失败不改变数据库正式状态；
- 同一同步任务重复执行结果一致；
- 旧版本不能覆盖新版本；
- 未批准的迁移分类不参与正式提案。

## 8. Git 与发布流程

### 8.1 Git

- 使用私有 GitHub 仓库；
- `main` 始终保持可运行；
- 每个任务使用短期分支；
- 一个任务一个主要提交或一组紧密提交；
- 合并前必须通过 CI 和 Review；
- 不在提交信息中包含学生姓名或业务隐私。

### 8.2 环境

- Local：本机开发；
- Test：自动测试数据库；
- Staging：使用假数据或脱敏数据验证部署；
- Production：正式数据，仅主 Agent 或人工批准发布。

### 8.3 发布

```text
任务完成
→ CI 通过
→ Reviewer 无阻塞问题
→ Staging 部署
→ 手工流程验证
→ 创建数据库备份
→ 人工批准
→ 生产部署
→ 运行健康检查和关键流程
```

Subagent 不得自行推送生产、执行数据库破坏性迁移或轮换生产密钥。

## 9. 小白学习顺序

不要先系统学习所有技术，只在当前阶段学习必要部分：

1. Git 基础：提交、分支、diff、回退；
2. Django：模型、迁移、表单、视图、模板；
3. PostgreSQL：表、索引、事务、备份与恢复；
4. Docker Compose：启动、停止、日志、卷；
5. HTTP 和 OAuth 基础；
6. 飞书开放平台应用与权限；
7. Linux：SSH、文件权限、system logs、磁盘空间；
8. 域名、DNS、HTTPS 和防火墙；
9. AI 结构化输出、重试和调用成本；
10. Staging、监控、备份和故障处理。

每项学习都必须对应一个可执行结果。例如学习 PostgreSQL 备份时，完成一次真实备份和恢复，不只看教程。

## 11. 项目完成定义

MVP 只有同时满足以下条件才算完成：

- 数据库是唯一正式写入口；
- 当前和未来课表完成迁移和对账；
- 管理员可以手工安全排课；
- 多人修改不会静默覆盖；
- 个人课表不受飞书 200 视图限制；
- AI 能从真实调课文本生成可确认的结构化需求；
- 候选均来自确定性引擎且无硬冲突；
- 飞书同步幂等、可重试、可对账；
- 生产环境有 HTTPS、监控和异地备份；
- 已实际完成一次恢复演练；
- 影子试点和真实试点均有记录；
- 所有阻塞 Review 问题已经解决；
- `docs/README.md`、领域词汇、ADR 和 Runbook 与代码一致。

## 12. 立即执行的第一批任务

按顺序执行，不并行写代码：

1. 创建私有 GitHub 仓库并配置当前仓库为远程；

3. 建立 Django + PostgreSQL 最小项目；

5. 建立 `make setup/dev/test/check`；

7. 用只读 Scout 分析 `data/private/` 中的 CSV 和字段；
8. 主 Agent 根据分析结果继续逐项确认领域决策；
9. 领域模型获业务负责人确认后，才启动阶段 2 的排课核心实现。
